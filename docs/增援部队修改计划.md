# 增援部队修改计划

日期：2026 年 10 月 12 日

本计划用于将增援部队逻辑对齐《增援部队.docx》及用户确认的出生点规则。核心修改包括地面增援出生点、独立操作、空军人员自动行军、交战阻塞和歼灭条件。已完成核心服务端修改和自动回归，尚未部署。数据库迁移及客户端实机联调待验证。

## 1 规则依据与范围

- 规则来源：用户提供的《增援部队.docx》。
- 已确认补充：主力在前线 C，最近主城为 A，增援应在 A 附近的城市 B 出生，再向 C 行军；地面增援不能直接把 A 当作默认出生点。
- 对照范围：本地服务端增援生成、移动、交战、汇合和清理逻辑。客户端操作能力与线上运行版本需要在实施时验证。
- 购买增援产生的队伍与空降后拆分返航的运输机队应明确区分，避免仅凭 `reserve` 模板将两种生命周期混为一谈。

## 2 各类增援的目标行为

| 主力类型 | 人员增援 | 载具增援 | 出生与初始移动 |
| --- | --- | --- | --- |
| 步兵 | 步兵 | 载具 | 最近主城 A 附近的己方城市 B 出生，自动向主力 C 行军 |
| 装甲 | 装甲成员 | 装甲 | 同地面增援规则 |
| 侦察 | 侦察兵 | 载具 | 同地面增援规则 |
| 飞机 | 飞行员 | 飞机 | 最近主城附近己方机场出生；人员自动向主力行军，飞机原地等待玩家指令 |
| 伞兵 | 伞兵 | 运输机 | 最近主城附近己方机场出生；人员自动向主力行军，运输机原地等待玩家指令 |

地面载具与所有人员增援可单独操作，手动命令的目的地必须为己方城市。飞机和运输机增援只能手动前往己方机场，允许进入己方机场防守局。目的地限制不应用于地面行军的中途节点：途经敌情应按交战规则处理，途经未占领城市可以穿过，不占领城市。

## 3 修改项目

### 3.1 修正地面增援出生点

修改前：`war_campaign/supply.py` 中 `_nearest_supply_city` 从主力位置搜索己方补给网内的带⭐主城，`column_route` 直接使用该主城作为出生点。缺少选取主城附近城市的步骤。

计划：

1. 根据主力位置 C 选择最近主城 A。
2. 在 A 附近选择满足归属和部署条件的己方城市 B。
3. 从 B 生成增援队，自动寻路前往 C。
4. 将主城选择与出生城市选择拆成两个独立步骤；路线预检、即时出队和库存排队后出队共用同一套规则。
5. 同城出生时继续处理汇合，但不得为避免同城汇合而擅自改选其他主城。

主要入口：`war_campaign/supply.py` 的 `_nearest_supply_city`、`column_route`、`spawn_supply_column`。

验收：构造主力 C、最近主城 A、候选城市 B 的地图，确认增援出生位置为 B，移动起点为 B，目的地为 C。

### 3.2 允许增援独立操作并校验目的地

修改前：`handlers/war_at.py` 的 `handle_transport_commandnode` 对所有 `reserve` 单位直接返回不可部署，人员和载具增援均无法手动移动。

计划：

- 按增援携带的资源、对应主力类型及队伍来源识别人员、地面载具、飞机和运输机。
- 人员与地面载具允许发起移动和在途改道，校验最终目的地属于己方。
- 飞机与运输机允许独立转场，仅接受己方机场，不能因机场正在防守交战而一律拒绝。
- 城市目标和部队目标解析后均应用相同限制，避免通过不同目标类型绕过校验。
- 同步检查客户端拖拽、目的地选择、箭头和响应处理，确保服务端放行后玩家可以实际下令。

主要入口：`handlers/war_at.py`、`war_campaign/at_movement.py`、`war_campaign/at_ops.py`。

验收：己方城市可下令，敌方及未占领城市不可作为目的地；己方机场可转场并进入防守局，敌方机场和普通城市不可作为飞机增援目的地。

### 3.3 区分空军人员与飞机的初始行军

修改前：`spawn_supply_column` 对空军及伞兵主力的所有增援统一在机场原地等待，人员队也不会向主力自动行军。

计划：

- 保持人员与载具分队生成。
- 飞行员和伞兵增援在出生机场生成后，自动选择到达主力的路线。
- 飞机和运输机增援留在出生机场，等待玩家下令；应具备正确的机场、移动方式和展示数据。
- 保留资源汇合及编制封顶机制，并分别核对人员队主动到达、主力到站、玩家指挥飞机转场后汇合的行为。

主要入口：`war_campaign/supply.py` 的 `spawn_supply_column`、`merge_waiting_columns` 和 `_arrive_supply_column`。

验收：一次空军补给生成两队，人员队开始行军，飞机队保持待命；伞兵和运输机同样分别处理。

### 3.4 实现交战阻塞和无对应主力时的保护状态

修改前：`advance_movements` 对增援队跳过途经交战检查，到达时只执行汇合、追赶或解散；未实现进入对局后被卡住的状态。

计划：

- 途经需要进入对局的城市时中止后续行军，记录增援队与该对局的关联。
- 将“被对局阻塞”与“贡献战斗资源”分开处理。
- 对应主力不在该局时，增援队不向战斗资源池提供兵力，不产生战斗影响，也不受普通战损和战斗结算扣减，但不能继续穿过该局。
- 单独处理包围歼灭，不能把保护状态实现为绝对不会被歼灭。
- 对局结束时清除阻塞关联；恢复行军、驻留或重新寻路方式按确认后的规则执行。
- 对应主力就在该局时，补给汇合与进行中战斗资源池同步应保持一致，避免只更新战略地图资源而战斗内仍无新增兵力。

主要入口：`war_campaign/tick.py` 的移动推进、会战关联与结算；`war_campaign/supply.py` 的汇合；必要时联动 `matchmaking.py` 和 `force_pool.py`。

验收：无对应主力的局可以卡住增援，战斗资源总量不变，普通战损不影响增援；未占领且无敌情的城市可以穿过且不被增援占领。

### 3.5 补齐增援自身的歼灭条件

修改前：普通补给队清理主要检查对应主力是否缺失或已删除，没有增援自身被包围或周围无可用己方机场的判定。

计划：

- 人员与地面载具：按确认后的包围规则判定并歼灭。
- 飞机与运输机：周围没有可用己方机场时判定歼灭。
- 对应主力消失时，清理其购买增援队；空降拆分返航机队是否同样处理需单独确认。
- 清理应一次性删除移动、对局关联、资源及展示数据，避免残留箭头、交战状态或 OnTheWay 数量。

主要入口：`war_campaign/supply.py` 的 `_cleanup_supply_columns`、移动及会战结算相关清理流程。

验收：主力仍存在但增援满足包围条件时能够歼灭；飞机无可用己方机场时能够歼灭；存在合法出路时不得误删。

## 4 已确认规则与实施边界

用户已确认：

| 规则 | 实施口径 |
| --- | --- |
| 主城附近城市 B | 与 A 直接通过补给线相连的己方城市，优先选到主力行军时间最短的 B；没有 B 时从 A 出生 |
| 手动指令 | 到达玩家指定的己方城市或机场后驻留，遇到对应主力时汇合 |
| 对局结束 | 解除交战阻塞，自动重新追赶主力；飞机仍受己方机场和运输半径限制，无法合法追赶时原地等待 |
| 包围检查 | 入局立即检查，并在阻塞期间定期检查；无友方邻城撤退路线时歼灭 |
| 可用机场 | 对应主力模板的运输半径内、属于己方的机场；允许防守交战机场 |

本次采用的实施方式：

- 最近主城保留己方补给网内带⭐主城的候选条件，按行军耗时选择；地面增援使用带权最短时间寻路。
- 保留旧客户端显式指定合法出生城市的入口；未指定或指定无效时使用 A → B 自动选择。
- 购买增援用 `command_nodes.supply_state` 记录来源、手动指令和阻塞关联，空降拆分返航机队沿用原有独立生命周期。
- 受到对局阻塞的增援不加入 `war_battles.factions`，通过独立关联恢复地图交战显示，避免被当作普通参战部队计入战损或资源池。

交战边界已确认：途经敌城但没有现成对局时，有敌方主力驻军则停住等待，不主动创建对局；敌方空城可以穿过但不占领。仅驻军阻塞不按“进入对局”进行包围歼灭，实际进入对局后才应用入局及周期包围检查。

## 5 实施顺序

1. 按已确认规则区分增援类型和队伍来源，持久化独立指令及阻塞关联。
2. 修正地面出生点选择，统一预检、出队和排队交付入口。
3. 区分空军人员与飞机的初始移动，开放独立操作并增加目的地限制。
4. 实现对局阻塞、保护状态、释放及资源池同步。
5. 补齐包围与机场不可用歼灭、主力消失清理及展示数据删除。
6. 更新与文档冲突的旧测试，完成自动回归和客户端联调。

## 8 RTS 可靠性补充修复

2026 年 10 月 12 日继续复查后，补充修复以下问题：

| 问题 | 修复方式 |
| --- | --- |
| 普通主力跨段漏检 | 按路线顺序处理所有已跨过的中间城市，保存移动进度；一次 tick 跨多个节点也不会绕过敌驻军或漏掉占城 |
| 补给推送失败重复发放 | 生成增援、扣库存、更新主力、删除订单共用一条连接和外层事务；提交后再推送，失败不重新交付 |
| 生产失败重复入账 | 各阵营库存和生产游标共同提交；持锁后重读游标，避免并发消费相同周期 |
| 对局结束后增援误歼灭 | 先判断关联对局是否结束，再检查仍在进行中的对局包围条件 |
| 失效队头堵塞 | 检查库存前先清理部队已消失和数量无效的订单；有效但资源不足的队头仍按 FIFO 等待 |
| 并发首开多场战争 | 数据库事务级咨询锁串行化查询、创建、城市归属和初始库存初始化；初始化失败全部回滚 |
| 野外增援穿过对局 | 单独关联补给线会战，冻结剩余行军，不加入参战资源和普通战损；结束后恢复，仍在交战时检查撤退路线 |

进行中对局的补给资源池同步推迟到数据库提交之后，回滚不会提前给战斗资源池增加兵力。

新增测试 `tests/test_rts_reliability.py`：覆盖故障重试、事务取消、并发交付与开战、晚到 tick、多节点占城、野外阻塞及释放、资源池提交时序。数据库外的 17 个测试通过；另有 3 个独立 PostgreSQL 集成测试，因为未设置 `HNG_RTS_TEST_DSN` 而跳过，不计入通过数量。

PostgreSQL 集成测试使用随机命名的临时 schema，并在测试结束后删除。配置独立测试数据库后，可运行：

```sh
HNG_RTS_TEST_DSN='postgresql://user:password@localhost/test_database' .venv/bin/python tests/test_rts_reliability.py
```
